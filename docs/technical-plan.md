# 语音互动网页密室逃脱：技术方案草案

更新时间：2026-10-24

状态：技术讨论与实现记录，允许随实现结果调整。当前已有初始网页原型，七牛接口尚未联调；启动方式见根目录 README.md。

## 1. 项目方向

开发一款用于开放 AI 比赛的语音互动网页密室逃脱游戏，接入七牛灵矽 AI 平台。

- 比赛在开发者自己的电脑上运行，可以控制浏览器版本和实验功能开关。
- 游戏包含多个固定视角房间，通过房间切换、查看物件、操作道具和解谜推进流程。
- 玩家可以与不同房间中的 NPC 互动，并在探索或互动后获得道具。
- 界面包含道具栏；主角状态栏为当前设想，可能显示“虔诚度”等状态。
- 语音交互用于与 NPC 对话、描述线索和表达操作意图，对话内容能够影响身份暴露风险。
- **正式游戏过程全程由语音控制**：进入持续聆听会话后，移动、查看地图、观察场景、使用或交付道具、NPC 对话及界面开关均不依赖鼠标或键盘；不采用按住说话或按键确认。
- 画面包含暗角、故障、晕眩等氛围效果。
- 背景暂时考虑与邪恶宗教组织有关：玩家在收集线索的同时，需要避免被识破为“异类”。
- 现阶段主要确定框架能力；完整故事、主角身份、规模及具体谜题尚未确定。

## 3. 玩法框架与暂定背景

本节区分已经提出的框架能力、当前玩法设想和待定细节，不将故事方向视为已经定稿的剧本。

### 已提出的框架能力

- **多房间探索**：各房间使用固定视角，拥有自己的物件、NPC 和交互入口；通过语音指定目的地并切换房间，保留已发生的变化。
- **道具栏**：展示持有的道具；道具可以来自房间探索或 NPC 互动，通过语音查看、使用或交给指定 NPC，不依赖选择格子或拖拽。
- **NPC 互动**：不同 NPC 具有各自的身份、可知信息及交互条件；对话能够提供线索、触发事件或给予道具。
- **NPC 差异**：每个 NPC 具有独立音色、人设、表达方式及每局对话记录；性格通过角色配置与提示词表现，剧情权限和道具发放由后端规则管理。
- **地图**：通过“看看地图”等自然语言打开，通过语音查看地点、选择可达目的地或关闭地图；地图界面不要求点击房间。
- **线索与进度记录**：框架记录已发现的信息、触发的事件和谜题进度；是否提供独立线索手册界面待定。
- **跨场景条件**：在一个房间或 NPC 处获得的道具、线索和剧情标志，可以影响其他房间的交互。

### 全程语音交互：已确定的框架约束

- 正式游戏保持持续聆听，自动判断说话开始和结束；不需要按住麦克风按钮、按空格或使用鼠标。
- 支持同义表达和当前语境，不将下面的示例句子限定成唯一有效口令。
- 系统操作、角色行动和 NPC 对话需要按语境区分。“看看地图”“暂停游戏”等系统操作不应作为对 NPC 的发言，也不应因此改变虔诚度。
- 道具交付等角色行动可以引发 NPC 反应，由游戏规则决定其结果；系统界面操作与角色在故事中做出的行动不能混为一谈。
- 理解“这个”“他”“刚才那个房间”等指代时，使用当前查看的物件、交谈对象与历史语境；目标不唯一或识别不确定时，通过语音追问，不误执行。
- 地图、道具详情、线索和设置等界面，均应具备语音打开、浏览、切换、返回和关闭路径。
- 支持语音暂停与继续，并设计语音打断 NPC 播报的行为；暂停时除恢复控制外不推进故事和状态。
- 显示聆听、识别、处理、播报、暂停、重连等状态，以及识别文本和执行结果，帮助玩家判断系统是否理解。
- 房间、人物、物件需要可被说出的名称或描述；发现新内容时通过场景、字幕或语音提供必要信息，让玩家无需鼠标悬停即可理解可交互对象。

| 语音表达示例 | 框架行为 |
| --- | --- |
| “把铜钥匙给守夜人” | 解析道具与接收者，后端检查持有、人物位置与交付条件，再结算并播放回应 |
| “去走廊” | 检查当前可达性和剧情限制，执行房间切换并播报必要反馈 |
| “看看地图” | 打开地图展示当前地点与已知区域，不作为 NPC 对话 |
| “看看我的东西” | 展示或聚焦道具栏，可继续用语音查看某件道具 |
| “看看桌上的账本” | 聚焦并放大目标，展示或读出可知内容 |
| “关掉地图”“返回房间” | 关闭当前信息层并返回场景 |

浏览器的系统级麦克风授权与音频初始化在进入正式游戏前完成；这与游戏内的持续语音操作分开处理。具体启动流程需在本机原型中验证。

### 主角状态与身份暴露：当前设想

- 主角可能有状态栏，其中一个状态暂称“虔诚度”（用户讨论中的“虞诚程度”暂按此理解）。
- 当前更适合将该数值理解为玩家表现出来的虔诚、或被组织视为同类的可信程度；是否代表角色真实信仰尚未确定。
- 对话内容会引起虔诚度变化；当其低于一定阈值时，其他角色可能识破玩家为“异类”，触发被抓走等后果。
- 初步体验循环：探索房间、与 NPC 对话、获取道具与线索，同时维持身份，避免暴露。
- 具体状态名称、量表、初始值、每次变化幅度和暴露阈值均未确定，不在当前框架记录中固定数值。
- 目前不额外确定其他人物状态；恐惧、理智、体力等仅在后续确有玩法需要时再讨论。

### 对话判定的实现建议

- AI 分析对话语义，提出对应的游戏事件或受限的状态变化建议，由 Go 后端按规则结算。
- 道具发放、状态变化和暴露后果统一由后端确认，不能只根据 NPC 的自然语言回答修改状态。
- NPC 回应应依据结算后的结果，避免口头表示“获得道具”但实际没有入包，或已经被抓却继续正常交谈。
- 对改变状态的回合记录识别文本、意图类型、目标、判定依据和结算结果，便于调试语音识别错误或不合理判定。
- 切换房间、对话打断或网络重连后，不应重复发放道具或重复扣除同一回合的状态。
- NPC 获取与其身份相符的信息，区分“游戏系统知道的事实”与“这个 NPC 知道的事实”；是否共享怀疑或警报另行设计。

### 语音意图与 NPC 交互：补充设计记录

- AI 根据当前场景和语境判断系统操作、场景行动或 NPC 对话，提出受限的结构化操作；Go 后端校验对象、前置条件并结算，前端展示结果。
- 否定、询问和引用不能按字面关键词直接执行；对象不明确时语音追问。一次行动可以同时引发 NPC 回应，但应先确认行动结果。
- 每个 NPC 分别维护音色、人设、可知事实和对话记录；改变音色不等于切换角色或清空上下文。
- 互动奖励采用预定义剧情事件：AI 识别允许的语义条件，Go 检查道具、线索和进度后发奖，成功后再生成交付台词。重复消息、打断或重连不能重复结算。
- 详细配置、事件示例及七牛音色 / 智能体切换边界见 [语音意图、NPC 角色与剧情交互设计](design/voice-and-npc.md)。这些属于后续方案，当前仍是关键词规则与浏览器语音原型。

### 支撑玩法的状态划分建议

以下是领域划分，尚不是最终接口或数据库结构。

| 对象 | 建议记录的内容 |
| --- | --- |
| 房间 | 当前房间、可进入的房间、物件和机关状态、NPC 所在位置 |
| 玩家 | 持有道具、已发现线索、暂定的虔诚度及当前是否被识破 |
| 道具 | 定义与实例、获得来源、持有与消耗状态、允许的使用目标 |
| NPC | 身份与角色设定、音色映射、可知信息、每局对话记录、交互条件、已触发的对话事件 |
| 剧情进度 | 事件标志、谜题进度、房间解锁条件、当前遭遇或结束状态 |

### 剧情进度与本地存档：推荐方案

- 用后端事件及前置条件管理剧情：已发现线索、持有道具、NPC 互动和已完成事件共同决定可达进度，允许多条线索并行积累。
- Go 通过 SQLite 保存每局状态快照、请求去重结果、事件记录及按 NPC 隔离的对话上下文；静态角色与剧本定义跟随项目保存。
- 每次有效回合完成时自动落盘；状态、道具、奖励标记和请求结果在一个事务内提交，成功后才向前端和语音反馈结果。
- 提供最近进度恢复和少量命名检查点。回档创建新局 / 分支，同时恢复该时点的世界与 NPC 记忆，隔离旧请求和迟到结果。
- 浏览器从后端定位自动存档槽，Go 重启或关闭浏览器后均可恢复；世界进度不依赖标签页存储。上述存档能力已接入当前规则原型，详细实现与后续设计见 [剧情进度与本地存档设计](design/progress-and-saves.md)。

### 故事与规则待定项

- 宗教组织、主角及 NPC 的具体设定，以及主角为何进入此处。
- 虔诚度是全局身份指标，还是需要结合各 NPC 的独立判断。
- 状态栏显示精确数值、模糊等级，还是主要通过 NPC 反应传达风险。
- 暴露是否立即导致失败，或先出现试探、警告、抓捕、逃脱及补救机会。
- 什么言行会提高或降低虔诚度，以及玩家如何理解这些规则。
- 房间数量、NPC 数量、道具使用方式及谜题依赖关系。

## 4. 前端渲染分工

### PixiJS 场景

- 渲染房间背景、门、柜子、道具等场景内容。
- 根据语音操作结果处理物件聚焦、放大、状态变化和场景动画，提供操作结果的视觉反馈。
- 给场景整体或局部物件应用滤镜与自定义 shader。
- 固定视角可以通过图片、透明物件图层、缩放和视差表现空间感，当前不引入自由移动的 3D 房间。

### React 界面

- 负责道具栏、地图、暂定的主角状态栏、设置、字幕、语音会话状态和弹窗等界面。
- 界面是语音驱动的显示层，所有游戏内功能具有语音操作路径；道具格子、地图地点和导航提示不要求点击。
- 界面是否参与场景特效，按具体体验决定；普通 DOM 可以用于保持文字与信息展示清晰。
- 常驻语音区展示波形、当前聆听状态、识别文本及结果；不设计按住说话按钮、键盘提示或必须点击的确认控件。
- 前端界面状态与后端游戏状态分开管理。

### HTML-in-Canvas

- 游戏启动前强制检查所需实验 API，再实际绘制双色 HTML 元素并核对 Canvas 像素；全部通过才加载游戏。接口缺失、绘制异常、像素不符或 5 秒超时均阻止进入游戏、演示或调试模式。检测页后台时取消、回前台重试，不采用普通 HTML 降级体验；浏览器开关仅作启用指引，不假定网页可读取其状态。
- 用 HTML/CSS 编写终端、电子门锁、对讲机面板、文字线索等内容。
- 将元素绘制成纹理后参与 Canvas 渲染，使文字和界面能够一起出现故障、扭曲等 shader 效果。
- HTML-in-Canvas 是 DOM 到纹理的能力，PixiJS 负责场景与特效，两者需要适配；不假定 PixiJS 已提供开箱即用的集成。
- 普通透明 Canvas 覆盖在网页上，无法直接读取并扭曲底下的 DOM；需要把目标内容实际接入纹理和渲染流程。

## 5. 氛围特效方向

| 效果 | 初步实现思路 |
| --- | --- |
| 四周变暗、视野收窄 | 径向遮罩或暗角 shader |
| 灯光闪烁、短暂黑屏 | 亮度、遮罩及时间动画 |
| 故障、扫描线、画面撕裂 | 噪声、分段位移与扫描线 shader |
| RGB 错位 | 对颜色通道分别偏移采样 |
| 晕眩、失焦、画面晃动 | 镜头变换、模糊及位移 shader 组合 |
| 终端文字与按钮一起变形 | HTML-in-Canvas 纹理接入后处理 |

优先尝试 PixiJS 及 pixi-filters 的现有滤镜，再按视觉目标编写自定义 shader。特效的持续时间、强度、渐入渐出和触发时机由前端统一管理。

特效可以与剧情、对话或暴露事件联动，例如被 NPC 试探时视野收窄、暴露时画面出现故障。具体映射尚未确定，不将所有状态降低都固定表现为晕眩。

强烈非线性扭曲应优先验证文字、物件与状态反馈是否仍可辨认。由于正式游戏全程语音控制，shader 形变后的鼠标命中映射不作为核心玩法的前置要求；若后续保留开发调试控件，再单独处理其坐标与交互。

## 6. Go / Gin 后端分工

- 管理每局游戏的会话、多个房间、NPC、谜题、道具、主角状态和剧情进度。
- 连接七牛平台，处理鉴权、设备身份、语音和控制消息的适配。
- 接收并执行 AI 的结构化操作，检查前置条件后更新状态。
- 编排 AI 的意图判断与 NPC 回应，校验其解析的道具、人物与房间目标；不明确时返回语音澄清请求。
- 结算对话对虔诚度等状态的影响，以及条件满足时的身份暴露和抓捕等事件。
- 向浏览器同步游戏状态、剧情事件和特效参数。
- 浏览器负责逐帧动画和 GPU 渲染，后端不传输逐帧特效画面。

基本原则：AI 负责理解玩家表达和生成角色回应，游戏规则由代码判定。移动、地图、道具及对话统一从语音意图进入后端规则，不以鼠标或键盘操作作为替代前提。

例如，玩家说“用铜钥匙打开左边柜子”，AI 提出使用道具的操作，后端检查钥匙与柜子状态，成功后通知前端开柜，再将执行结果提供给 AI 继续回应。

## 7. 七牛与浏览器语音接入

- 平台 REST API 主要用于智能体、设备等管理，实时语音使用平台 WebSocket 协议。
- 初步采用“浏览器连接 Go 后端，Go 后端连接七牛”的适配方式，平台密钥留在后端。
- 浏览器使用 getUserMedia 与 Web Audio / AudioWorklet 采集和处理音频。
- 正式游戏优先验证平台实时对话模式，持续聆听并自动判断语音边界，不采用按键开始与结束录音的交互方式。
- 需要验证环境噪声、回声及游戏自身 TTS / 音效不会被误识别为玩家指令；玩家开口打断时，需要同步停止旧播报并清理播放队列。
- 需要验证输入音频的重采样与分帧、返回音频的解码与连续播放、字幕事件和打断时的播放队列清理。
- 平台文档支持 PCM / Opus 输入，输出音频章节描述为 Opus；具体实现以目标环境的协商参数和联调结果为准。
- AI 操作游戏可以优先验证平台的 MCP 工具调用链路，具体工具由本项目定义。
- NPC 人设可对应智能体的 `systemPrompt`，音色映射到 `ttsVoiceId`；连接握手选择智能体与会话内切换音色是不同操作，角色记忆由游戏后端隔离维护，具体流程见补充设计。
- 开发环境使用 localhost 或 HTTPS，在正式游戏开始前完成麦克风授权和音频初始化；会话建立后的全部游戏操作走语音。

## 8. 本机实验环境与待验证事项

本阶段接受 HTML-in-Canvas 的实验性依赖，不将跨浏览器兼容或公开部署作为前置要求。

1. 确定并记录比赛使用的 Chrome / Chromium 版本及 HTML-in-Canvas 开关；必要时使用 Canary。官方提案提供了 `chrome://flags/#canvas-draw-element` 开关说明。
2. 根据目标版本确认 HTML-in-Canvas API。旧示例使用 `layoutsubtree`，近期设计使用 `content="drawable"` 和子元素的 `drawable` 属性，纹理上传 API 也有调整。
3. 验证 HTML 元素到 PixiJS 纹理的适配，包括更新、尺寸变化、清晰度和资源释放。
4. 验证 shader 形变后的内容可读性，以及语音指令触发的聚焦、放大与界面开关。
5. 验证七牛对纯软件终端的设备注册、绑定和会话隔离方式；现有协议仍按设备身份建模。
6. 跑通真实音频收发与工具调用，再确定编解码实现及会话恢复方案。
7. 在比赛电脑上同时运行语音与多层特效，测量帧率和交互延迟，再确定效果预算。
8. 验证语音转写、NPC 对话、道具发放、状态变化和暴露事件之间的一致性，以及跨房间状态保留。
9. 验证不依赖鼠标或键盘完成移动、道具交付、地图打开与关闭、语音澄清、暂停与恢复。
10. 验证实时聆听、播报打断、回声处理和掉线恢复，确保恢复后不重复结算且无需按键重新开启录音。

## 9. 建议的分阶段验证原型

以下保留验证方向，并记录本轮原型进度。

### 当前实现进度（2026-10-24）

- 已从 v2 概念图切出房间、头像和道具素材，并补充一张同风格走廊背景。
- 已实现 React 界面、PixiJS 场景与氛围 shader，HUD、道具栏、对话和地图均为可更新组件。
- 已实现 Gin 会话、HTTP / WebSocket 控制，以及规则驱动的换房间、查看地图、调查账本、道具交付、手记、虔诚度和暂停 / 恢复。
- 已提供浏览器持续语音识别、语音合成与首次授权入口，另有无需麦克风的自动演示。
- 已提供启动前的 HTML-in-Canvas 接口、实际绘制与像素强制自检，以及账本纹理适配代码；检查失败只展示说明，已移除普通 HTML 游戏内回退。本机 Chrome 已实测自检通过后进入游戏，内置浏览器缺少接口时被拦截。自检验证 DOM 到 2D Canvas 的绘制，账本纹理与 shader 完整链路仍需单独联调。
- 目前 AI 理解由本地示例规则代替，七牛实时语音、设备注册与真实麦克风条件下的完整联调仍待完成。
- 已接入 SQLite 自动存档、持久化请求去重、当前守夜人对话记录与命名检查点；回档同步恢复世界与对话、创建新分支并拦截旧请求，开发阶段结构变更可直接调整并重建存档，不实现旧格式兼容。

### 第一阶段：验证渲染与语音链路

- 一个固定视角房间，包含少量可操作物件。
- 一块通过 HTML-in-Canvas 接入的 HTML 终端。
- 暗角、故障、晕眩三种可由语音或测试剧情事件触发的效果。
- 浏览器与 Gin 后端的 WebSocket 通信。
- 一次完整的语音输入、AI 回答与音频播放。
- 持续聆听与自动语音边界检测，以及一次玩家开口打断 NPC 播报的流程。
- 一次“语音操作 → 后端判定 → 场景变化”的闭环。

### 第二阶段：验证玩法框架

- 两个可切换的固定视角房间，用来验证跨房间状态。
- 少量测试 NPC、道具和线索，不依赖正式剧本。
- 一次“NPC 互动获得道具 → 道具进入道具栏 → 在另一房间使用”的完整流程。
- 全程不用鼠标或键盘，完成指定道具交给指定 NPC、语音移动，以及地图打开、查看和关闭。
- 一次目标存在歧义时的语音澄清，以及一次系统操作不影响 NPC 对话与虔诚度的验证。
- 一个暂定的虔诚度状态，验证不同对话触发变化，并在阈值条件满足时进入暴露或抓捕的测试事件。
- 验证重复消息与对话打断不会导致道具或状态重复结算。

上述数量与事件只用于验证框架，不构成正式关卡规模或最终故事设定。

剧情、关卡数量、画风和最终目录结构，待原型验证后继续调整；本地存档优先采用上述 SQLite 方案，具体结构与实现继续验证。
