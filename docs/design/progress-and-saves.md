# 剧情进度与本地存档设计

更新时间：2026-10-24

状态：存档层已接入当前规则原型。SQLite 保存当前世界、事件、请求结果、守夜人对话记录和命名检查点；刷新、关闭浏览器或重启服务后恢复最近进度。正式多 NPC 剧情与 AI 上下文编排仍待实现，初始世界、物品及角色配置已外置。

## 1. 推荐结构

- **Go 游戏规则管理进度**：记录已发生的事实，以事件前置条件决定下一步能否发生。
- **SQLite 保存每局进度**：本机数据库由 Go 读写，不需要另启数据库服务。
- **JSON / YAML 保存静态内容**：房间、NPC、人设、物品定义、剧情事件、条件和效果跟随项目版本管理。
- **浏览器保存入口信息和偏好**：例如上次使用的存档 ID、音量；真实背包、剧情和 NPC 状态从 Go 读取。
- **当前状态快照 + 结算记录 + 检查点**：直接读快照恢复游戏；结算记录用于去重与调试；检查点用于指定位置的演示与重试。

SQLite 适合设备本地数据与应用文件，无需数据库运维；支持将同一事务内的修改一并提交或回滚。采用本方案的依据见 [SQLite 适用场景](https://sqlite.org/whentouse.html) 与 [事务说明](https://sqlite.org/transactional.html)。本机低并发阶段先采用默认日志模式与可靠的同步设置；是否引入 WAL 由实测需要决定。

数据库默认放在 `.local/data/nightwatch.db`（相对项目根目录，通过 `NIGHTWATCH_DB` 覆盖；`.local/` 已被 Git 忽略）。程序启动后创建目录并检查数据库版本；网页通过 `POST /api/sessions/resume` 原子地读取或创建自动存档。静态剧本和媒体素材不必复制进每份存档，初始世界、物品和 NPC 定义已外置到 `internal/content`。

实现使用 `modernc.org/sqlite v1.61.0`，最低 Go 版本随驱动更新为 1.26。SQLite 是唯一世界状态来源，操作失败时无需回滚额外的内存副本；本机阶段顺序结算、单数据库连接、默认回滚日志、`synchronous=FULL` 与连接级外键 / 超时设置。

## 2. 剧情如何推进

每局保存一组真实状态与已完成事件，而不是只保存一个章节号。多个支线或不同房间的线索可以并行积累；每次动作或对话结算时，由后端检查相关事件是否满足条件。

| 进度内容       | 示例                                                |
| -------------- | --------------------------------------------------- |
| 位置与世界状态 | 当前房间、已访问房间、门锁、机关、物件是否被取走    |
| 玩家状态       | 道具及数量 / 实例、已知线索、虔诚度、是否暴露       |
| NPC 状态       | 所在位置、当前剧情阶段、已知事实、已经完成的互动    |
| 剧情状态       | 已完成事件、谜题进度、分支选择、已解锁区域、结局    |
| 对话语境       | 当前交谈对象、待澄清的对象、各 NPC 必要的对话上下文 |

例如后续关卡可以配置以下依赖，仅为框架示例，并非当前原型已开放内堂：

1. 调查账本后记录 `ledger_seen`。
2. 归还铜钥匙后完成 `keeper_accept_key`，取得通行凭。
3. 玩家试图进入内堂时，检查 `ledger_seen`、持有通行凭、身份未暴露等条件。
4. 条件满足才执行进入事件，并保存新房间与进度；未满足时提供与当前知识相符的反馈。

一次性事件依靠稳定的事件 ID 与每局完成记录去重。确需重复的事件额外定义次数、冷却或发生序号；不把“玩家说了同样的话”当成同一次请求，也不因换了说法就重复发奖。

AI 根据当前场景和允许的判据提出操作或事件建议；事件是否可触发、产生什么效果，以后端定义和已存事实为准。读取存档不会重新询问 AI 过去是否成功，也不会重跑过去的剧情事件。

## 3. 存什么、何时存

最小阶段可将动态世界状态作为 JSON 存入 SQLite；需要唯一约束、排序和检索的请求、事件与检查点单独建表。暂不要求把每件物品和每个布尔标志拆成独立表。

| 逻辑表         | 作用                                                                      |
| -------------- | ------------------------------------------------------------------------- |
| `runs`         | 每局 ID、存档槽、状态版本、剧本版本、状态 JSON、最近保存时间、是否结束    |
| `commands`     | 每局请求 ID、输入摘要、真实识别文本或引用、结算结果；断线重试时返回原结果 |
| `events`       | 已提交事件及发生顺序、触发回合、效果与依据；一次性事件具有每局唯一约束    |
| `npc_memories` | 按每局与 NPC 保存近期已完成对话、受限的历史摘要；摘要关联已处理回合       |
| `checkpoints`  | 命名检查点、来源局与版本、完整世界快照和对应 NPC 记忆                     |

当前已建立上述五类表，另有 `sessions` 保存稳定会话与当前分支的映射、`slots` 定位自动存档。`runs.state_json` 包含状态版本与剧本版本；`commands` 保存输入哈希和原结算结果；当前 `events` 保存已完成标志与暴露事件，`npc_memories` 保存守夜人的实际交互原话。未来的结构化 NPC 事实属于世界状态，语言摘要属于对话上下文，摘要不能覆盖真实剧情事实。

自动保存以**有效回合结算**为单位：房间移动、物品取得 / 消耗 / 交付、发现线索、谜题与分支、状态变化、NPC 对话记忆。纯字幕逐字输出、波形变化和动画帧无需写盘，语音中间识别结果不推进剧情。

关键操作遵循如下顺序：

1. 取得当前状态和版本，在数据库事务外完成必要的 AI 理解。
2. 对同一局顺序结算，重新验证相关条件与版本，检查请求是否已经执行。
3. 在一个短事务中写入新状态、相关事件、确定的角色事实和请求结算结果。
4. 提交成功后通知前端同步最新状态，随后按结算结果生成 / 播放 NPC 回应。
5. 回应完成后补存对应对白。生成或播放失败不撤销已提交的奖励；恢复时仍能依据结构化事实继续。

例如“扣除铜钥匙 + 加入通行凭 + 写入已领取事件 + 保存请求结果”必须一起成功，避免重启后只少了钥匙却没有奖励。写盘失败时保留原状态，明确反馈没有完成，不先展示成功。

请求去重已经落盘，不再限制为最近 256 条结果。同一局相同请求 ID 返回原结算；相同 ID 携带不同输入会被拒绝。事件完成标记解决玩家主动再次领取的问题，请求 ID 解决网络自动重试的问题，两者同时保留。

## 4. 继续游戏、重开与检查点

建议先提供一个自动存档槽，支持以下语音能力，表达不限于示例原句：

- “继续上次进度”：读取最近一局已提交状态。
- “保存为入堂前”：在当前稳定状态创建命名检查点。
- “回到入堂前”：从该检查点创建新的演示分支。
- “重新开始”或“重置进度”：新建一局，重新初始化世界和 NPC 记忆，原存档保留用于演示恢复。系统设置面板只提供重置进度，通过语音执行。

重启 Go 后从 SQLite 恢复最近进度；浏览器关闭后，重新打开也能由后端定位自动存档，不仅依靠标签页的 `sessionStorage`。浏览器上的存档 ID 仅是入口，必须验证有效且与当前选择一致。

加载检查点时：

1. 检查存档与剧本版本；取得同一时点的世界状态、已完成事件和所有相关 NPC 记忆。
2. 新建 `run_id`，将这份检查点作为新一局 / 分支的起点，继承检查点前已经完成的事件与奖励状态。
3. 不继承检查点之后的对话、事件和旧请求结果；新请求使用新 ID。旧分支暂停写入，保留以便恢复和排查。
4. 切换当前局与连接版本，终止旧 AI 回合及播报，拒绝旧连接迟到的状态和工具写入。
5. 前端从新局状态重新绘制，按需要播放房间转场，不重新执行检查点之前的动作。

这避免回档后 NPC 还记得未来谈话、道具和领取记录不一致，以及旧网络重试把新分支污染的问题。

比赛演示可准备少量经过实际游玩验证的命名检查点，例如“初入房间”“道具交换前”“身份即将暴露”。检查点应包含完整状态与角色记忆，不单独修改一个章节或房间字段来假造进度。

## 5. NPC 记忆与恢复边界

- 每个 NPC 按 `(run_id, npc_id)` 隔离对话；只恢复其在该局该时点能知道的事情。
- 保存少量近期原话和较早对话的摘要，后端筛选当前可知事实后再构建模型上下文；不把全局日志直接交给所有 NPC。
- 记忆摘要是可更新的辅助信息，不能作为唯一发奖依据。已完成事件、道具和暴露状态直接读取结构化存档。
- 游戏恢复点是最近一次已提交的结算。未完成的语音识别或 AI 推理可以取消；已结算但还没播出的结果仍然有效。
- 不恢复原麦克风连接、TTS 播放位置、音频缓冲和短暂 shader；根据世界状态重新建立语音会话与界面。必要时只补一句事实概述，不自动重放奖励操作。
- 若后续有钟声倒计时等玩法，需要明确记录游戏时间、剩余时长与暂停策略；目前不默认让关闭网页的现实时间推进剧情。

## 6. 版本与演示备份

开发阶段以最新数据库和内容结构为准，不实现历史格式迁移或兼容适配；结构变化时可直接调整并重建开发存档。当前格式标识仅用于发现不匹配，避免把错误结构读取成有效进度。

初期至少准备当前自动存档与几个命名检查点；本机数据需要迁移到另一台演示电脑时，导出一致的数据库备份和匹配的项目版本。运行中导出可采用 [SQLite Backup API](https://sqlite.org/backup.html)；若采用文件复制，先完整关闭数据库连接后再复制，不直接复制正在写入的主文件。

本地存档支持本机恢复。动作和存档操作先提交再由灵矽播报；开放式 NPC 对话在云端成功后提交。播报失败不撤销已保存的动作；语音识别本身不推进回合。

## 7. 当前实现与验证

- `session.Service` 经事务接口调用 SQLite 存储适配器，原有规则仍负责游戏结算。
- 已实现后端自动存档定位、网页启动恢复、保存 / 列出 / 加载命名检查点，以及重开时新建分支。
- `State.id` 为稳定会话 ID，`State.runId` 为每局 / 分支编号；回档和重开后 `revision` 保持递增。HTTP 与 WebSocket 命令必须携带原始 `runId`，传输重试保留该编号，旧分支的新操作返回冲突；已提交请求的重试仅返回原结果。
- 当前守夜人对话按分支持久化，系统操作不写入 NPC 对话。多 NPC 与 AI 记忆摘要在后续接入。
- 已覆盖重启恢复、奖励事务回滚、并发 / 重复请求、检查点恢复角色记录与事件、旧分支隔离、存档结构不匹配和 HTTP / WebSocket 错误恢复的测试。

网页验证通过开发转写注入走同一条指令链路：保存“初见”、交付钥匙、进入走廊、刷新、真实重启服务后再次读取，确认房间 / 通行凭 / 虔诚度保留；再读取重启前的“初见”，确认恢复铜钥匙与初始状态。真实麦克风与七牛联调仍另行验证。`go test -race ./...` 与前端构建通过。
