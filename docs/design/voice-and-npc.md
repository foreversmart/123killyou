# 语音意图、NPC 角色与剧情交互设计

更新时间：2026-10-24

状态：框架设计草案，随故事与七牛联调结果调整。本文中的工具、配置和事件字段均为本项目拟定的设计，不是已经实现的接口，也不是七牛原生字段。

## 1. 已确认的方向与实现边界

- 正式游戏按住空格说话、松开发送，移动、道具与交互目标仍由语音表达，不要求鼠标选择或拖拽。NPC 回复期间按住空格会先打断，再打开识别；未按键时关闭识别，避免误收录 NPC 音频。
- 玩家说完一段已识别的有效发言后，必须得到回应。没有命中剧情、命令或关键词，不是丢弃输入或保持沉默的理由；回应可以是不推进剧情的闲聊、拒绝或澄清。
- AI 理解玩家意图、解析对象并生成角色回应；Go / Gin 后端检查条件、结算剧情和维护真实状态；React / PixiJS 展示结果。
- 每个 NPC 具有不同音色、性格、表达方式和可知信息，能够在交互中提供线索、给予或接收道具、触发剧情。
- 故事、人名、具体音色、条件和数值尚未确定。下文角色与事件仅用于说明框架。
- 当前原型使用灵矽语音识别，Go 关键词规则负责动作和奖励结算；已接入灵矽虚拟设备 OTA 激活、智能体绑定、云端台词与 PCM 音频播放，灵矽为必需依赖，云端失败明确报错，无需实体硬件。已有归还铜钥匙取得通行凭的规则示例，多 NPC 与独立音色仍按同一适配器扩展。

## 2. 谁决定一句话是对话还是行动

AI 的意图判断结合当前房间、可交互对象、背包、当前查看的物件、交谈对象与最近语境；后端负责确认解析结果中的对象是否真实存在、当前是否可执行。

| 类型       | 示例                                 | 处理方式                                                         |
| ---------- | ------------------------------------ | ---------------------------------------------------------------- |
| 系统操作   | “看看地图”“暂停游戏”                 | 更新系统界面或会话控制，不作为 NPC 听见的发言，不因此改变虔诚度  |
| 场景行动   | “去走廊”“把铜钥匙给守夜人”           | AI 提出结构化操作，Go 检查通路、物品、人物及剧情条件，再更新状态 |
| NPC 对话   | “你为什么守在这里？”                 | 选定 NPC，以其可知信息和性格回答，按受限规则评估可能的剧情事件   |
| 目标不明确 | “把这个给他”，但没有唯一的物件或人物 | 语音澄清，保留待补充的操作，不先执行                             |

拟定义的能力包括 `open_map()`、`move_to(room_id)`、`inspect(target_id)`、`give_item(item_id, npc_id)`、`talk_to_npc(npc_id, utterance)`；它们是逻辑能力，具体 MCP 工具划分在接入时确定。

- 理解否定、询问与引用：“我不去走廊”不执行移动；“你要这把钥匙吗？”先作为询问，不直接扣除道具。
- 同一句话可以既有行动又有对话。行动先结算，NPC 随后按实际结果回应；多个行动按依赖顺序处理，前一步失败时不默认继续后续操作。
- 同房间多人时，使用明确称呼或当前交谈对象；仍有歧义则追问。称呼和系统目标由后端验证，不能让模型任意选择不在场人物。
- 场景内确实没有听众时，不凭空产生 NPC 回应。旁白或系统反馈有独立的说话者身份。

### 2.1 每轮都要有反馈

| 情况                              | 应有表现                                                                          | 状态约束                                       |
| --------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------- |
| 对 NPC 说完全无关的话、闲聊或玩笑 | 当前 NPC 按性格接话，再自然转回当前情境。例如“西瓜？这时候你倒有闲心。先说来意。” | 普通跑题不自动扣虔诚度，不发奖、不推进剧情     |
| 询问 NPC 不知道的事               | 用人设内的“不知道”、推托或反问回答                                                | 不编造剧情事实，也不伪装成语音识别失败         |
| 指代、人物或行动目标不明确        | 简短追问缺少的内容，后续设计保留待补充意图                                        | 澄清之前不执行操作                             |
| 动作受阻、物品缺失、NPC 不在场    | 说明具体失败原因，必要时指出可做的下一步                                          | 不用沉默表达失败，不描述尚未成功的行动         |
| 当前房间没有 NPC                  | 由系统或旁白明确回应当前情况                                                      | 不让不在场角色隔空接话                         |
| 听到部分话语却未获得完整转写      | 提示“刚才那句话没有听完整，能再说一遍吗？”                                        | 不把残缺文本提交成剧情操作                     |
| 模型、网络或语音服务失败          | 明确反馈暂时中断或超时；可用时保留字幕、继续聆听                                  | 不让玩家无限停在“正在理解”；不能假称操作未执行 |

语义理解与回应生成分开：无法识别为行动的正常发言，优先进入当前 NPC 的对话；对话可以没有任何剧情事件，但必须有台词。接入七牛时，在共同约束和各 NPC 提示词中写入此规则；模型返回空白或调用失败时显示灵矽服务异常，不通过本地 NPC 台词或浏览器语音合成替代。

输入一进入处理就展示聆听、理解或回应状态，最终给出字幕和启用声音时的读白。纯静音不反复催促；环境噪声与已判定的播放回声不作为游戏回合。玩家主动打断时可以取消旧台词，已经提交的剧情结算保留，迟到结果不能覆盖新回合。

当前落地范围：浏览器不再使用 Web Speech API，按住空格经 AudioWorklet 采集 PCM 并持续上传，松开后发送 `listen.stop`，由灵矽返回完整 STT。一次最长录音 30 秒，识别连接总时限 45 秒，松开后云端识别时限 10 秒，网页等待最终文字最多 12 秒。静音、轻点和取消不产生回合，迟到结果不进入新回合。识别连接收到 STT 后立即终止自动回复，不向网页传递该连接的音频。Go 据文字判断动作：明确动作先保存并推送 `type=action`，再调用灵矽 TTS；开放式 NPC 对话仍需云端返回后复核版本并提交。所有 NPC 台词和播报来自灵矽，无本地替代。播报失败不撤销已完成动作，错误提示区分识别失败、请求失败和已执行但播报失败。NDJSON 字幕 / PCM 即时推送，播放器约缓冲 120ms 开始连续播放。界面保留录音、识别和回复状态，移除“听见你说……”转写显示。

这两类失败必须区分：没听完整时可以重说；请求超时时后端可能已经结算，反馈先引导确认当前情况，不自动用新请求 ID 重复执行。实际播报、回声与服务中断恢复仍需比赛浏览器和真实麦克风联调。

## 3. NPC 定义与每局状态分开保存

性格主要通过提示词表现；音色是语音合成配置；拥有的道具、可触发事件和剧情权限由后端规则表达，不能只写在提示词里。

| 部分         | 建议字段 / 内容                                             | 维护位置                       |
| ------------ | ----------------------------------------------------------- | ------------------------------ |
| 身份与表现   | `id`、称呼及别名、所在房间、头像、可选表情资源              | NPC 静态配置                   |
| 性格与表达   | 动机、态度、措辞、句长、说话习惯、对试探的反应              | NPC 静态配置 / 提示词模板      |
| 音色         | 内部 `voiceProfile`，映射到平台音色 ID 及已验证的语速等参数 | 后端平台配置                   |
| 知识边界     | 知道的事实、可能隐瞒的信息、满足条件才能透露的事实          | 后端按当前进度筛选后提供给模型 |
| 交互定义     | 可接受的物品、可参与的剧情事件及事件前置条件                | 后端事件配置与规则             |
| 每局角色状态 | 最近对话、已被告知的事实、已触发事件、当前态度或剧情阶段    | 当前游戏会话，按 `npc_id` 隔离 |

不因框架设计直接新增一套“好感度 / 信任度 / 怀疑度”数值；确有玩法需要再引入。当前虔诚度仍是暂定的主角指标，各 NPC 可以根据各自性格对同一事实作出不同反应。

拟定配置示例：

```yaml
id: keeper
name: 守夜人
aliases: [看门人]
room_id: watch
portrait: /art/portrait-keeper.webp
voice_profile: keeper_low_male # 项目内部别名，实际平台音色 ID 待选
personality:
  traits: [寡言, 多疑, 重视规矩]
  speaking_style: 短句，语气平静，常用反问，不主动解释规矩的来历
  motivation: 确认来者身份并守住入口
knowledge_set: keeper_facts
interaction_ids: [keeper_accept_key]
```

角色提示词由“共同的游戏交互约束 + 角色人设 + 后端筛选的可知事实 + 当前角色状态 + 当前回合结算结果”组合。示例表达：

> 你是守夜人。寡言、多疑，重视规矩，用短句回应。只依据本回合提供的可知事实作答；对未知之事按人设推托，不补造剧情事实。道具交付与剧情推进以工具返回结果为准，成功后再描述已完成的行为。

仅靠“不要剧透”的提示词不能隔离知识：模型不应收到整份剧本、其他 NPC 的私密对话或尚未解锁的谜底。模型生成的猜测和对白也不能自动写成游戏事实。

## 4. 独立音色、角色切换与记忆

- 逻辑上每个 NPC 一份角色配置和一份每局对话记录；这不要求每个 NPC 使用不同大模型，也不要求所有 NPC 同时维持在线连接。
- 后端确定 `speaker_id` 后解析对应音色，前端同步展示头像、称呼、字幕和正在说话的状态。系统反馈与旁白使用独立声线或清楚的视觉标识，不伪装成 NPC 发言。
- 初期可为少量 NPC 预配置七牛智能体，复用模型但配置不同人设与音色，按当前交谈对象使用对应配置；切换连接时恢复该 NPC 的必要上下文。最终连接策略以联调延迟和上下文隔离结果确定。
- 每局事实与角色记忆由 Go 管理，平台聊天记录或长期记忆不作为剧情状态的唯一来源；重开游戏后不得带入上一局对话与奖励进度。
- 本地持久化、重启恢复与回档时的角色记忆一致性见 [剧情进度与本地存档设计](progress-and-saves.md)。
- 同一场景多人交谈时先支持顺序发言，明确下一位说话者，不同时混播多路语音。
- 播放队列关联 `session_id`、`turn_id`、`speaker_id` 和角色切换版本。玩家按下空格打断、切房间或更换对象时清理旧音频，拒绝旧回合迟到的字幕与语音；已完成的游戏结算保留。

当前代码位于 `internal/integration/linx/`：管理 API 只准备 `1024-keeper`；虚拟设备复用持久化身份和 OTA 令牌。`recognition.go` 使用 manual 模式转发麦克风 PCM、接收 STT 并终止自动回复；回复连接使用经过 Go 规则处理的文字生成台词或 `text_response` 播报。会话层通过接口使用识别和回复适配器，动作先结算、随后播报，开放式对白仍先生成再提交。音频只暂存内存，不进入 SQLite / 检查点。多 NPC 自动切换仍待实现，详见 [灵矽虚拟设备接入](../development/linx.md)。

七牛文档中已经确认的能力与限制（2026-10-24 核对）：

- [智能体 API](https://linx.qiniu.com/docs/xrobot/api/agent) 提供 `systemPrompt`、`ttsVoiceId` 等配置，可查询可选音色。
- [智能体与音色切换](https://linx.qiniu.com/docs/xrobot/platform/agent-voice-switch) 区分连接握手的 `X-Agent-ID` 与会话中的 `listen.agent_params.voice`：前者选择智能体，后者只改变音色且保留上下文。不能把换音色当作角色和记忆切换。
- [WebSocket 协议](https://linx.qiniu.com/docs/xrobot/platform/websocket) 描述了握手时的提示词占位参数、实时聆听及打断消息。不能据此假设可以在任意回合无缝热换整份系统提示词。

待联调：连续聆听时的音色切换时机、切换确认与首句延迟；智能体连接切换与上下文恢复；多局 / 多 NPC 的历史隔离；工具结果是否能在生成交付台词前返回。若平台默认自动回复不能满足结算顺序，应调整编排或语音接入路径，不能靠前端改字幕掩盖音频已经播错的问题。

## 5. 交互中如何触发道具与剧情

采用“预先定义剧情事件，AI 识别语义与提出事件，Go 检查并执行”的方式。AI 可以理解灵活表达，但不能任意创造道具或直接设置背包、虔诚度和任务完成状态。

每个事件包含：稳定 ID、参与 NPC、触发类型、前置条件、一次性 / 可重复策略、状态变化和成功 / 失败后可用于回应的事实。前置条件只引用后端已有事实；涉及对话语义时单独列出允许评估的判据。

现有“归还钥匙 → 获得通行凭”的概念配置如下，具体字段尚未实现：

```yaml
id: keeper_accept_key
npc_id: keeper
trigger:
  type: give_item
  item_id: key
requires:
  room_id: watch
  npc_present: true
  player_has_item: key
  player_not_caught: true
  event_not_completed: keeper_accept_key
effects:
  remove_item: key
  add_item: permit
  set_flag: keyDelivered
reply_fact: 已收到铜钥匙，并把通行凭交给玩家
once_per_session: true
```

完整处理顺序：

1. 玩家说“这是你的钥匙，收好”，AI 解析为把 `key` 交给 `keeper`。
2. Go 检查当前房间、人物在场、背包和事件进度；工具调用关联当前会话与真实输入回合。
3. 后端在一次结算中扣除钥匙、加入通行凭、写入事件完成标记，返回稳定的事件 ID 和状态版本。重复请求只返回原结果，不重复发物品。
4. 前端更新道具栏并提示获得物品；AI 收到成功事实后，以守夜人的性格组织台词，再用守夜人的音色播报。
5. 条件不满足时返回明确原因，NPC 依据失败结果回应，不描述交付成功。语音服务失败也不撤销已完成的道具结算，重试播报不重新执行事件。

普通对话也可以发放道具。例如暂定事件“向书吏问起被划掉的名字后得到残页”：后端先要求玩家已调查登记册、书吏在场且奖励未领取；AI 只判断玩家本轮是否确实询问了这个话题，Go 据此尝试结算已定义的事件。角色和内容只是示例，不确定为正式剧本。

对于“说服成功”“表现虔诚”等语义条件，需要给 AI 明确、有限的判据，例如是否主动表明来意、是否表达指定立场，并返回判据 ID 与原话依据；不让它自由决定奖励种类或扣分幅度。模型判断仍可能出错：关键进度优先依赖可核对的道具、线索与剧情事实；歧义时追问，不凭模糊表述发奖或处罚。

不对模型开放通用的 `grant_item(any_id)`、`set_devotion(any_value)` 等任意写状态工具。拟采用 `resolve_interaction(npc_id, interaction_id, evidence)` 一类受限入口；后端验证事件确属该 NPC、当前回合有效且条件满足，效果取自后端定义。同一回合的相互依赖效果一起提交，不能扣了道具却漏发奖励。

## 6. 状态、对白与打断保持一致

- 事实确认前，可以生成不承诺结果的短回应或展示思考状态；“给你了”“门打开了”等确认语句必须等待结算成功。
- 玩家说“谢谢”或重复询问，不重新发奖；奖励去重依赖每局事件标记与请求 ID，不能只依赖模型记忆。
- 玩家打断交付台词时，已入包物品保留，可以通过语音查看背包；中断的是播放，不自动回滚游戏操作。
- 每局写状态的操作顺序处理。AI 回答期间若玩家已经换房间或改变状态，提交前重新检查相关条件，不执行过时请求。
- 系统界面操作默认不会向 NPC 泄露地图、背包或设置内容；实际展示物品、递交道具等世界内行为才进入相应 NPC 的记忆和事件逻辑。

## 7. 后续最小验证范围

- 两个测试 NPC，采用不同性格、头像与音色；同一个问题能体现不同表达，且知识边界不同。
- 从明确称呼到省略指代的交谈对象选择，以及多人歧义时的语音澄清。
- 一次道具交换事件、一次普通对话触发的奖励事件；验证前置条件未满足、已领取和重复消息。
- NPC 播报中途打断、切换人物和房间，确认旧音色、字幕与迟到工具结果不串入新场景。
- 重连、刷新、重开一局后，验证角色记忆、道具、剧情进度和奖励去重的一致性。
- 对 NPC 连续说多个无关话题和无意义但已转写的内容，确认每轮都有角色回应；拿到奖励后再闲聊不索要已经交出的物品。无 NPC、动作失败与指代不清均有系统反馈，普通跑题不改变游戏进度。
- 验证空模型输出、云端识别空结果、识别连接中断、HTTP 超时和响应体卡住；确认能再次按住空格说话，纯静音不产生重复催促，超时不自动重复交付。
- 先验证结算顺序与音色切换，再扩展角色数量、关系状态与正式剧本。
